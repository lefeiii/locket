# Notification email setup

1. Run **all** of `supabase/email_notifications.sql` in Supabase → SQL Editor. It installs its own tables, policies, event triggers, grouping, and unsubscribe functions. It expects the existing Locket application tables (`users`, `stories`, `comments`, `story_follows`). No other new migration is required.
2. GitHub → lefeiii/locket → Settings → Secrets and variables → Actions → **Variables** → New repository variable: `EMAIL_NOTIFICATIONS_ENABLED` = `true`. The existing repository **secrets** `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `GMAIL_APP_PASSWORD` are reused. Never put the service role key in a public environment variable.
3. Log into Locket → notification settings (`/settings`), select email choices and save. Existing users start with email off. Their login email must be verified.
4. Test using two accounts: subscribe to account A's public story with account B; opt B into story emails. Post a linked update with A. For reply emails, opt A into replies and comment with B. Run **Locket notification emails** from GitHub Actions, or wait for the schedule. Reply emails become eligible one hour after the first reply; additional replies in that hour are grouped. Story updates are eligible immediately. The schedule checks every 15 minutes, subject to GitHub delays.
5. Confirm inbox delivery, follow the story link, and test the unsubscribe link (click Unsubscribe to confirm). No login is required to unsubscribe. Email content excludes story titles, bodies, and usernames.

The bell remains unchanged. Emails cover subscribed story arcs and replies on one's own stories; reactions and persona follows do not email. Private, diary-only, hidden, unverified, self-reply and opted-out events do not send. Queues start only after installation and opt-in; there is no historical backfill.

The Gmail account authenticates via its existing app password. This workflow sends at most 20 messages per run; it is a modest-volume starting point, not a high-volume mail service. Monitor Actions and `email_delivery_queue` for status and backlog without copying addresses or tokens into logs. `sent` means Gmail accepted the SMTP submission, not confirmed inbox delivery. `claimed`/`uncertain` rows are never automatically retried because SMTP could have accepted a message before the connection failed. A crash after claiming can lose a notification; investigate before manually retrying. Disable the repository variable to stop delivery immediately. Deleting a user or story cascades its queued entries.
